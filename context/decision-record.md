# Decision Record

These are my decision records and thought process throughout planning & development, in chronological order.

## Scaffolding

- `2026-11-21 09:49` **Turborepo**: best fit for managing multiple apps in one repo; global root commands (build, lint, test) plus caching.
- `2026-11-21 09:53` **pnpm** `minimumReleaseAge` **7 days + pinned Node version**: security; defends against supply-chain attacks from malicious newly published packages, and keeps the runtime on a known, patched release.
- `2026-11-21 09:55` **Husky, set up early**: enforces codebase conventions from day one, so both AI agents and humans follow the same rules.
- `2026-11-21 10:21` **Reusable prompts in** `.agents/prompts/`**, before development starts**: streamline the workflow (PRD, plan, execute, explain, commit, docs cleanup) so each step is repeatable; `.agents/` keeps them tool-agnostic rather than tied to one AI tool.
- `2026-11-21 10:48` **React + Vite + TypeScript for the frontend**: simple, agent-native (LLMs write it well), scales as the app grows, and fits a single-page upload-and-report UI.
- `2026-11-21 11:00` **FastAPI + uv for the backend**: simple, agent-native, and scalable; FastAPI's Pydantic models fit structured LLM output, and uv manages Python itself plus a lockfile, so setup is one tool.
- `2026-11-21 11:12` **Bruno for API testing**: collections are plain-text files in the repo (versioned and reviewed with the code), offline, no account needed; the collection lives in `backend/bruno/` and can run in CI through the Bruno CLI later.
- `2026-11-21 11:18` **Dockerize early**: a working baseline before development starts; `docker compose up -d` runs the full stack with only Docker installed, and CI builds and health-checks both images on every push.
- `2026-11-21 11:33` **nginx serves the frontend and proxies** `/api` **to the backend**: `vite preview` is not meant for production; the proxy avoids CORS and baking the backend URL into the build. Vite's dev proxy mirrors it, so frontend code always calls `/api`. Assumes no cloud deployment for this task; a static host (Vercel, Netlify, S3 + CloudFront) would replace nginx.
- `2026-11-21 11:39` **actionlint + act for CI changes**: actionlint catches workflow mistakes in the pre-commit hook and in CI; act runs the `ci` job locally (`pnpm ci:local`) and catches problems actionlint cannot, such as a missing action version.

## Design

- `2026-11-21 12:09` **Initial high-level design directions written before system and solution design** (`context/direction.md`): sets the architectural rules (async, agnostic, modular, design patterns, evals) and frontend conventions up front, so every later design decision and task is checked against them instead of being retrofitted. These are a starting point and will be tweaked as the system and solution design take shape.
- `2026-11-21 14:27` **Rejected files pause the job until the analyst decides** (`context/architecture.md`): when some files in an upload are rejected, the job waits instead of processing the rest. The analyst re-uploads the rejected files, continues without them, or cancels. The consolidated report needs full context to be correct; silently dropping a document can change the conclusion, for example a market analysis behind a trade, or identifying suspects from evidence documents. If the analyst continues without them, the report lists the excluded files so the gap stays visible.
- `2026-11-21 14:32` **Orphaned files are cleaned up, not prevented**: if a file is stored but creating its job fails, a retention rule or cleanup job deletes it later. Making file storage and job creation atomic would add complexity for a harmless, rare case.
- `2026-11-21 14:33` **Postgres as the job store and the queue** (`context/architecture.md`): a Postgres-backed queue library (Procrastinate or PGQueuer, the Python equivalents of pg-boss) lets the API create a job and enqueue it in one transaction, so a crash between the two cannot strand a job. This avoids an outbox or sweeper and keeps results across restarts. This decision is for the assignment; the alternative production design (SQS with an outbox) is in `context/architecture.md`.
- `2026-11-21 14:39` **Action endpoints for job state changes** (`POST /jobs/{id}/confirm`, `POST /jobs/{id}/cancel`): `confirm` names what the analyst does, accepting the final set of files, rather than what the system does next. Action endpoints are clearer than a bare `POST /jobs/{id}`, whose meaning is ambiguous, and simpler to validate than `PATCH` with a status field. Invalid actions for the job's current state return `409 Conflict`. Cancel is a `POST` rather than `DELETE` because the job is kept with status `cancelled`.
- `2026-11-21 14:45` **SQS with an outbox for the production queue** (envisioned AWS architecture, not for this POC): SQS is managed, takes queue load off the database, has built-in dead-letter queues, and lets ECS scale workers on queue depth. Because SQS and RDS cannot share a transaction, the API writes the job and an outbox row together, and a relay publishes to SQS. The POC keeps the Postgres queue; both sit behind the same create-and-enqueue adapter operation, so the switch needs no API changes.
- `2026-11-21 14:46` **Adapter pattern for external dependencies** (`context/architecture.md`): the queue, job store, file storage, and LLM provider each sit behind an interface with one adapter per provider. The POC runs on Postgres, local storage, and a mock or hosted LLM, and production can swap to SQS, S3, and Bedrock or another provider without changing API or worker logic. It also lets tests and CI run on a mock LLM with no API key, and follows the agnostic direction in `context/direction.md`.
- `2026-11-21 15:09` **Fixed LLM pipeline, not an agent** (`context/architecture.md`): the steps (extract, guardrails, document summary, consolidation) are known in advance and always run in the same order, so an agent deciding what to do next adds cost, latency, and unpredictability without adding value. A fixed pipeline is also easier to evaluate, because each step has a defined input, output, and eval set. An agent may still suit the optional feature, such as Q&A over the documents. Anthropic's workflows-versus-agents guidance supports this (`context/industry-insights.md`).
- `2026-11-21 15:18` **Polling `GET /jobs/{id}` for status and results** (`context/architecture.md`): the frontend polls one endpoint with TanStack Query every 1–2 seconds, only while the job is processing (`queued`, `running`, or `consolidating`). It does not poll while the job waits for the analyst (`awaiting_input`) or once it reaches a final state. Refresh and shared links work without extra logic because the URL holds the job ID, and the API stays stateless. Server-sent events are listed as an enhancement; they need a pub/sub layer and nginx changes, and would keep the same payload shape.

- `2026-11-21 15:47` **All prompts in one central file** (`backend/app/pipeline/prompts.yaml`, `context/architecture.md`): system prompts, user templates, and Jev questions live in one file that maintainers edit, instead of prompt text spread across pipeline steps. Each entry is versioned and validated at startup, the version is recorded with every LLM call and used in the cache key, and changes to the file trigger the evals.
- `2026-11-21 20:28` **MinIO for uploads** (`context/architecture.md`): for this POC, the API and worker store files in a local MinIO service through the S3 API, with no cloud account. In production the same adapter would point at AWS S3, and only the endpoint, bucket, and keys would change.
- `2026-11-21 21:50` **Limit errors return `422`** (`context/architecture.md`): an oversized file or a PDF with too many pages is a per-file rejection, and too many files is a `422` for the whole upload. A mixed upload still accepts the valid files and records the others as rejected, which is the same result the analyst already sees. The error codes stay `file_too_large`, `page_limit_exceeded`, and `file_count_exceeded`.

## Re-design based on Industry Practices

Sources and findings are in `context/industry-insights.md`.

- `2026-11-21 15:42` **Datamarking for document text in prompts** (`context/architecture.md`): Microsoft's spotlighting research found delimiters alone roughly halve prompt-injection success and can be faked, while datamarking cut it from about 50% to under 3% with minimal quality loss. The pipeline's LLM also has no tools, following OWASP's least-privilege guidance, so an injection can distort output but cannot trigger actions.
- `2026-11-21 15:42` **Contradictions surfaced with attribution** (`context/architecture.md`): multi-document summarisation research found LLMs usually collapse conflicting facts into one consensus value. The consolidation prompt asks for disagreements explicitly, and each contradiction in the report holds both claims with document, page, and quote. For an analyst, a hidden contradiction is as harmful as a missing document.
- `2026-11-21 15:42` **Source excerpts in the map-reduce combine step** (`context/architecture.md`): hierarchical merging gives more coherent long-document summaries than a running summary (BooookScore), and adding source excerpts during merging improves faithfulness (context-aware hierarchical merging).
- `2026-11-21 15:42` **Programmatic-first evaluation** (`context/architecture.md`): LLM judges overestimate faithfulness and score inconsistently across runs, and automatic factuality metrics can be gamed. Evals score schema validity, citation quotes, entity recall, and contradictions in code first, use an LLM judge averaged over several runs for coverage and conciseness, and add a human spot-check.

## Definition of Success

- `2026-11-21 16:05` **Eval sets written before implementation** (`backend/evals/golden.json`, `backend/evals/adversarial.json`, `backend/evals/fixtures.json`): success is defined up front as concrete cases and thresholds, so every phase is built to pass them instead of tests being fitted to whatever the code produces. The documents describe a fictional project, so the model cannot pass by recalling facts it already knows. The PDFs are generated from `fixtures.json`, so documents and expectations cannot drift apart. A canary string in every system prompt makes prompt leaks detectable in code.
