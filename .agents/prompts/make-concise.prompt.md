# Make concise

Rewrite the target Markdown file so it is short and easy to scan. Keep every fact, instruction, command, link, and code block that a reader needs. Cut words, not meaning.

## Cut

- Filler and throat-clearing: "It is important to note that", "In order to", "Basically", "As mentioned above".
- Repetition: the same point said twice, or a summary that restates the section it follows.
- Hedging and padding: "might possibly", "generally speaking", "a number of".
- Sentences that explain the obvious or describe the heading they sit under.

## Paragraphs

- One idea per paragraph.
- Split any paragraph longer than about four lines or three sentences.
- Prefer short, direct sentences in active voice.

## Structure

- One `#` title per file, describing what the file is.
- Use `##` and `###` headers so a reader can find a section by skimming. Headers are short noun phrases, not sentences.
- Order sections by what the reader needs first.
- Do not add a header for a section with only one line of content; fold it into a neighbour.

## Bullets

- Use bullets for lists of parallel items: options, steps, requirements, rules.
- Use numbered lists when order matters.
- Keep bullets parallel in grammar and roughly one line each. If a bullet needs more, it is probably a paragraph or a sub-section.
- Avoid nesting deeper than two levels.
- Keep prose for reasoning that connects ideas; do not chop an argument into fragments.

## Other formatting

- Use tables only for short, comparable facts.
- Put commands, paths, and identifiers in backticks.
- Use bold sparingly, for terms a reader must not miss.

## Do not

- Change meaning, technical details, or the file's scope.
- Remove links, code blocks, or commands unless they are duplicated.
- Compress into shorthand, arrows (`A -> B`), or undefined abbreviations. Concise still means full sentences a newcomer can read.

## Output

Edit the file in place. Then give a one-line summary of what was cut or restructured.
